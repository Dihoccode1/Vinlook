## Complete withdrawal snapshot — important proposed clarification

GET /pois/deletions accepts NO query parameters. Returns one complete response {data:{poiIds:[sorted unique IDs],snapshotId,generatedAt,complete:true},requestId}. No pagination/partial list: client applies only after full successful parse/validation, never clears local data merely because a request failed. snapshotId=SHA256 of canonical sorted IDs; generatedAt is server time of snapshot acquisition, not a global catalog sequence.

To avoid a stale offline POI reappearing when it was deleted then restored before that client synced, snapshot includes (a) all currently soft-deleted IDs, and (b) restored/nonpublic POIs whose publishedRevisionId=null but which retain at least one published historical revision. It excludes ordinary never-published drafts except already soft-deleted IDs allowed by D017. No draft contents, actors or reasons are exposed. Once a restored POI is published again, its ID leaves this withdrawal set. This explicitly expands D017's wording from currently deleted IDs to all historically published-but-currently-withdrawn IDs; approval is required. A tombstone does not delete immutable historical/media data on the server. Actual browser cache/player/route invalidation belongs to visitor/offline tasks.
